## Problem Statement

`dlls/` NPC tactical AI (HECU squads and friendly allies) is fixed decision-tree logic from 1998-era GoldSrc/HLSDK (`GetSchedule()` if/else chains). The goal, per `AGENTS_HYBRID_AI.md`, is to layer a modern Utility-AI tactical decision system on top of the existing execution infrastructure (schedules, tasks, nodegraph, navigation, animation, `scripted_sequence`, save/restore, `EHANDLE`) — the new layer decides *what* an NPC wants to do; existing HLSDK code keeps deciding *how*. This design doc covers only **Phase A**: the framework scaffolding that must exist before any NPC's actual behavior changes.

## What Makes This Cool

A GoldSrc mod with a debuggable, replayable AI decision layer — `ai_hybrid_debug 2` prints exactly why a grunt chose FLANK over COVER, with per-action scores, the first time this codebase will have that kind of introspection. Because the tactical core is deliberately kept free of engine dependencies, decisions become replayable outside the game entirely: capture a snapshot in-game, feed it to a standalone host binary, and get the same decision back — turning "the AI feels off in that one room" into a reproducible test case instead of a shrug.

## Constraints

- No gameplay changes may leak in during Phase A: `ai_hybrid` defaults to `0`, and even when enabled, Phase A must always resolve to `AI_ACTION_NONE` / no schedule override. `CHGrunt::GetSchedule()`'s existing return paths are untouched.
- No automated test suite exists anywhere in this repo today. Adding one for this subsystem is new territory, not an established pattern to copy.
- `-fno-exceptions` on Linux builds; no exceptions anywhere in new code.
- Engine SDK constraints: entities are engine-owned raw C++ objects (`CBaseEntity`/`CBaseMonster`), no dynamic linking against engine globals from outside a loaded game DLL, `EHANDLE` for cross-frame entity references, `TYPEDESCRIPTION`/`IMPLEMENT_SAVERESTORE` for persistence.
- Must not touch `dlls/master`'s actively-diverging Spirit of Half-Life (SoHL) backport work — `ext-ki` stays fully independent, no rebase planned.

## Premises

1. `ext-ki` stays fully independent from `master` (unrelated, actively-developed SoHL 1.2/1.4/1.5 backport work via many small PRs) — no rebase or merge planned.
2. `CHGrunt` (`dlls/hgrunt.cpp`) is the first reference implementation; all other NPC classes follow later, in the phase order `AGENTS_HYBRID_AI.md` defines.
3. **(Corrected during session)** Smoke tests and/or isolated unit tests should be added where technically feasible for the new AI logic (pure utility-scoring, confidence-decay math, cover-candidate scoring extracted as engine-decoupled functions) — in addition to, not instead of, "does it build" + manual in-game testing. Testability is a first-class design constraint for this new code, even though the rest of the codebase has none.
4. Phase A (framework scaffolding only: action enum, capability flags, master CVAR `ai_hybrid`, debug output plumbing) comes first, with **zero behavior change** while disabled — no tactical decision logic yet.

## Cross-Model Perspective

Codex's independent read (given the same problem statement, premises, and repo context, without seeing this conversation):

- **Coolest angle:** Build a "shadow brain" first — a deterministic, engine-free POD core that consumes an immutable snapshot and emits a decision record, but which always emits `AI_ACTION_NONE` in Phase A and never touches `GetSchedule()`. Its payoff is replay: capture compact debug snapshots in-game, replay them unchanged in a standalone host executable, and assert on decisions later — regressions become reproducible without constructing engine-owned entities.
- **Premise that changes Phase A most:** "the project has never had automated tests before, so testability is itself a design constraint on the new code, not a given." → the AI core must not become another `CBaseMonster`-coupled subsystem; the seam (engine adapter → immutable snapshot → pure core → inert decision/debug record) has to be established *before* any scoring logic is written, or every future test needs GoldSrc globals and entity lifetime machinery.
- **Existing pattern to borrow:** the shape of utility-AI frameworks like UnrealUtilityAI (action eligibility + score, a "brain" selecting the best, enter/exit separate from selection) and Source SDK's `SelectSchedule` seam (selection kept distinct from execution, with an oscillation monitor as a precedent against hidden thrashing). The GoldSrc-specific 50% still to build: the schedule adapter back to `GetScheduleOfType()`, fixed-size allocation-free snapshot/candidate arrays, the explicit ~4Hz decision clock with hysteresis/cooldowns, `EHANDLE` validation + field-by-field Save/Restore ownership, and trace/nodegraph candidate acquisition kept outside the pure scorer.
- **Weekend-scope Phase A:** `dlls/ai_hybrid_core.h/.cpp` (no HLSDK includes — enum, capability mask, `AIProfile`, POD memory/context/state/snapshot, action-name lookup, debug-record struct) + `dlls/ai_hybrid.h/.cpp` (the only engine-aware facade — CVAR reads, snapshot translation, bounded debug output) + CVAR registration in `game.cpp` + a dormant `AIHybridState` observed from `CHGrunt::PrescheduleThink()` with zero effect on `GetSchedule()`. No new `m_SaveData` fields yet (Phase A state is inert/resettable — persistence only from Phase B on). A minimal standalone test target (`tests/ai_hybrid_core_tests.cpp`, compiled with `-std=c++17 -fno-exceptions -fno-rtti`, no framework, no engine headers, no DLL link) covers only the pure functions that exist in Phase A: clamping, `ActionSupported`, `ActionName`, `DecayConfidence` boundary cases.

## Approaches Considered

### Approach A: Header-only core library
`dlls/ai_hybrid_core.h` holds structs/enums/pure `inline` functions only, no `.cpp`; `dlls/ai_hybrid.cpp` includes it and wires the CVARs + `PrescheduleThink()` debug hook.
Effort: S · Risk: Low
- Pro: minimal diff, no new translation unit in the build system, tests can include the header directly.
- Con: forces every constant/table into `inline`/`constexpr`; unwieldy and slows rebuilds once Phase B's scoring tables land (header re-included everywhere).
- Reuses: existing CVAR registration point in `dlls/game.cpp`, existing `PrescheduleThink()` hook (`hgrunt.cpp:363`).

### Approach B: Adapter/Core split (recommended)
`dlls/ai_hybrid_core.h/.cpp` (engine-free, POD-only, pure functions) + `dlls/ai_hybrid.h/.cpp` (sole engine-aware facade: CVARs, snapshot construction, debug output). A separate `tests/ai_hybrid_core_tests.cpp` compiles only against `ai_hybrid_core.cpp`, no DLL link.
Effort: M · Risk: Low
- Pro: makes the testability premise structurally true, not just declared — the core builds and tests without engine globals. Scales cleanly into Phase B/C (scoring, squad blackboard) without touching the adapter.
- Con: two new file pairs plus a test target to wire into both build systems (Linux `Makefile`, `.vcxproj`) for a phase that changes no behavior yet.
- Reuses: same CVAR site + `PrescheduleThink()` hook as A; `LAST_COMMON_SCHEDULE` pattern in `schedule.h` as the model for future `SCHED_ENHANCED_*` constants (not needed until Phase B).

### Approach C: Debug overlay first, core later
Before any `AIHybridState` exists, ship only an `ai_hybrid_debug` CVAR plus a function that prints, per tick, which schedule the *unmodified* original logic just chose and why (reconstructed from existing `bits_COND_*`/`m_hEnemy` fields). No new state, no snapshot, no core.
Effort: S · Risk: Low
- Pro: immediate value (visibility into existing AI decisions for the first time) and a reference log to diff the future hybrid core against in Phase B ("does disabled-hybrid behavior match logged original behavior?").
- Con: builds no utility-AI infrastructure at all — the actual Phase A deliverable from the spec (enum, capability flags, core scaffold) would effectively become "Phase A.5", diluting the spec's phase plan.
- Reuses: read-only access to existing `CBaseMonster`/`CSquadMonster` fields; no new files besides the debug function itself.

## Recommended Approach

**Approach B.** It's the only option that makes the session's corrected testability premise (#3) technically real rather than aspirational — A and C both leave the core either engine-coupled or nonexistent.

## Open Questions

- Where does `tests/` live and how does it build? Neither `linux/Makefile` nor the `.vcxproj` files currently define a standalone test target — this needs its own small build rule (likely a separate `make check` target on Linux; a minimal additional `.vcxproj` or a post-build custom step on Windows) before Phase B adds real logic to test.
- Should the CI workflow (`.github/workflows/ci-cd.yml`) run the new test target on every push, or is it a local-only dev tool for now? Not decided this session.
- Exact debug-output verbosity levels (`ai_hybrid_debug 0-3`) are specified in `AGENTS_HYBRID_AI.md` §36 — Phase A only needs level 0/1 (nothing / current+previous action, both `NONE`), levels 2-3 are Phase B+.

## Success Criteria

Phase A acceptance (per `AGENTS_HYBRID_AI.md` §47), adapted for the B split:
- Game DLL builds on both Linux and Windows, unchanged from today's build. The `ai_hybrid_core` standalone test target builds and its tests pass **on Linux** for Phase A; Windows/CI integration for the test target is an explicit follow-up (see Open Questions), not a Phase A success criterion.
- `ai_hybrid` master CVAR exists and works; default `0` means zero behavior change.
- `ai_hybrid_core` can be constructed/queried per NPC without needing a live game session (i.e., the standalone test binary runs and passes).
- `ai_hybrid_debug 1` reports action state (always `NONE`/`NONE` in Phase A) without spamming at debug `0`.
- No gameplay change while `ai_hybrid` is disabled (the default) — verified by manual play test, since no gameplay regression suite exists.
- Save/load unaffected (no new persistent fields added yet).
